# 官方小智 WebSocket 协议实录

> 实测环境：`wss://api.tenclass.net/xiaozhi/v1/`，2026-10 实测。
> 所有字段语义均在真实连接上验证过。

## 1. 连接与握手

### 请求头
```
Authorization: Bearer <token>      # 来自 OTA（见 OTA与绑定.md）
Protocol-Version: 1
Device-Id: <MAC 或任意设备标识>
Client-Id: <UUID>
```

### 客户端 hello（首包必须发）
```json
{
  "type": "hello",
  "version": 1,
  "features": {"mcp": true},
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

关键点：
- `features.mcp: true` —— **不声明这个，服务器不会下发 MCP 的 initialize/tools_list**。
- `frame_duration: 60` —— 声明 60ms 帧。实际上 PyAV 会把 60ms 输入拆成 3 个 20ms Opus 包，
  语义等价（总时长仍是 60ms），服务端 STT 正常。**不要试图"修"它**。

### 服务器 hello（响应）
```json
{
  "type": "hello",
  "session_id": "xxxxxxxx",
  "audio_params": {"sample_rate": 24000, ...}
}
```

- `session_id` —— **后续所有 listen/abort 报文都要带**。
- `audio_params.sample_rate` —— **下行采样率通常是 24000**（与上行 16000 不同！），
  解码器必须按这个值建。

## 2. 语音状态机

```
idle → listening → thinking → speaking → listening → ... → idle
```

事件（服务器下行 JSON）：

| type | 含义 | 关键字段 |
| :--- | :--- | :--- |
| `stt` | 语音识别结果（用户说了什么） | `text` |
| `llm` | 大模型返回（含情绪） | `text`, `emotion` |
| `tts` | 语音合成状态 | `state`: `start` / `sentence_start` / `stop`, `text` |
| `mcp` | 设备端 MCP 请求（需 `features.mcp`） | `payload`（JSON-RPC 2.0） |
| `system` | 系统消息 | — |

二进制帧 = 下行 Opus 音频（24kHz）。

## 3. 监听控制

### 开始监听
```json
{"type": "listen", "state": "start", "mode": "auto", "session_id": "<sid>"}
```

### 停止监听
```json
{"type": "listen", "state": "stop", "mode": "auto", "session_id": "<sid>"}
```

### 打断（她说一半时）
```json
{"type": "abort", "reason": "wake_word_detected", "session_id": "<sid>"}
```
`reason` 也可用 `user_interrupted`。

## 4. 两种监听模式的本质区别（实测）

| 模式 | 行为 |
| :--- | :--- |
| `auto` | 服务端听**一句**，生成 STT/TTS。`tts: stop` 后服务端**停止接收上行**。 |
| `realtime` | 服务端维持**连续监听**，一轮内可多段自动断句，支持说话中插话（barge-in）。 |

### ⚠️ auto 模式的核心坑
`auto` 模式下每轮 TTS 结束，**必须重新发 `listen start`**，否则第二句起全部被丢弃。

**这正是"连续对话第二句失聪"的头号根因。** 修法：监听 `tts: stop` 事件 → 延迟 250ms →
重发 `listen start`。

`realtime` 模式原生支持一轮内多段，不需要也不能重复发 `listen start`。

## 5. 会话断开是常态

服务端会周期性主动结束会话——**约 60s 没听到用户说话**就让助手道别并关闭 WebSocket
（客户端收到 `1005`）。

**这不是网络故障，是设计如此。** 客户端必须实现重连 + 自动恢复监听，否则用户每句话都要重新唤醒。

重连退避建议：1s 起、最多 5s；**连续失败才增长，一旦握手成功立刻重置回下限**
（否则每次都翻倍，用户要干等半分钟）。

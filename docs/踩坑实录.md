# 踩坑实录

> 这些坑全部在两台真实机器上踩过、定位过、验证过修复。**按价值排序。**

---

## 坑 1（★★★★★）：AEC 参考信号被放大 32767 倍，回声消除彻底失效

**症状**：扬声器放音时，助手被自己的声音"打断"，说话吞字、卡顿；有时能听到自己刚说的话被
当成用户输入重新回答。

**根因**：喂给 WebRTC APM 的 far-end 参考信号，在转 int16 时多乘了一次 32767：

```python
# ❌ 错误：ff 已经是 int16 量级，再乘 32767 → 每个非零样本都被 clip 成 ±32767 方波
fi = np.clip(ff * 32767.0, -32768.0, 32767.0).astype(np.int16)

# ✅ 正确：直接 clip 到 int16 范围
fi = np.clip(ff, -32768.0, 32767.0).astype(np.int16)
```

**为什么致命**：参考信号是"要消掉的目标波形"。把它变成方波后，AEC 的参考与实际回声
完全不相关 → 自适应滤波器无法收敛 → **回声一点没消**。

**实测数据**：

| 版本 | 输入回声 RMS | 输出 RMS | 抑制比 |
| :--- | ---: | ---: | ---: |
| 错误（×32767） | 3794 | 2316 | **4.3 dB** |
| 正确 | 3794 | 36 | **40.6 dB** |

**教训**：AEC 的 far/near 信号量纲必须一致；任何"顺手乘个系数"的代码都可能在
把参考信号变成垃圾。

## 坑 2（★★★★★）：auto 模式每轮结束必须重新 listen start，否则第二句全丢

**症状**：只能回答第一句，第二句完全没有反应。

**根因**：`mode="auto"` 下，服务端每轮 TTS 结束后**停止接收上行音频**。客户端不主动
重新 `listen start`，后续音频全被丢弃。

**修法**：监听 `tts: stop` → `sleep(0.25)` → 重发 `listen start`。

**实测**：不补发 → 6 句只中 1 句；补发后 → 6/6 全部识别。

## 坑 3（★★★★）：放音期回声回灌 → 云端 VAD 误判用户插话

**症状**：助手说话时经常"自我打断"，或者把自己刚说的话当成用户输入。

**根因链条**：
1. 扬声器声音被麦克风拾取（AEC 消不干净时）
2. 云端 VAD 检测到"有人说话"
3. 转写成幻听词（"嗯"、"不"、"哎对"）
4. 触发新 LLM 响应 → 打断当前 TTS

**权衡后的修法**（两条路）：

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| A. 阈值门控 | 消回声后残余 RMS < 阈值才置零 | 阈值一旦被大音量冲穿就失效（实测 2000 的阈值被 20000+ 的回声击穿） |
| B. **放音期硬闭麦** | `is_playing()` 期间上行 100% 置零 | 牺牲"说话中插话"，但**完全杜绝自打断** |

**推荐 B**：真打断交给**本地唤醒词**（走原始流，不受闭麦影响）或**鼠标点击**，
比指望云端 VAD 区分"回声 vs 插话"可靠得多。

**关键**：闭麦不能有任何 tail 延迟。实测证明，停止播放后加 250ms 静音尾巴，
会把用户**紧接着说的第一个字切掉**（"帮我..." 变成 "...我..."）。

## 坑 4（★★★）：tools/list 返回空 nextCursor 会死循环

**症状**：MCP 连接建立后，服务器以极高频率重复请求 `tools/list`（实测 12 秒 843 次）。

**根因**：返回结果里带了 `nextCursor: ""`（空字符串）。服务器把它当成"还有下一页"。

**修法**：**无更多页时直接省略 nextCursor 字段**，不要给空串。

---

## 坑 5（★★★）：通知（notifications/*）不要回复

**症状**：MCP 交互错乱。

**根因**：对 `notifications/initialized` 这类无 id 的通知，回了 `id: null` 的响应，
打乱了服务器的 MCP 客户端状态机。

**修法**：无 `id` 或 `method` 以 `notifications/` 开头的，一律**不回复**。

---

## 坑 6（★★）：websockets 库 12.x 与新版 API 不兼容

**症状**：`websockets.connect` 报 `TypeError`，或对象没有 `__aenter__`。

**差异**：

| 项 | 12.x (legacy) | 新版 |
| :--- | :--- | :--- |
| 自定义头参数名 | `extra_headers` | `additional_headers` |
| 连接对象 | **无 `__aenter__`**，不能用 `async with` | 支持 |

**修法**：两种都试 + `try/except TypeError` + 统一 `try/finally` 收尾。

---

## 坑 7（★★）：服务端 ~60s 静音主动断开（1005）是常态

**症状**：以为网络不稳，疯狂重连。

**真相**：服务端设计如此。收到 `1005` 后正常重连即可，别当故障处理。

**附带坑**：重连退避如果用"每次翻倍"（1→2→4→8→16→30s），用户要干等半分钟她才"活过来"。
应改成"连续失败才增长，握手成功立刻重置"。

## 坑 8（★）：麦克风权限 —— 从 .app 启动会拿到全零音频

**症状**：同一个 Python 解释器、同一段录音代码，**终端里跑有声音，双击 .app 跑全是 0**。

**根因**：macOS TCC 权限是按"启动它的那个进程"授予的。用 shell 脚本套壳的 `.app`
启动子进程，子进程拿不到麦克风权限，系统静默喂全零 PCM（不报错！）。

**修法**：从已授权的终端（或 IDE）启动；或正确注册 app bundle 并申请权限。

**排查技巧**：打印麦克风输入的**峰值**。恒为 0 就是权限问题，不是设备问题。

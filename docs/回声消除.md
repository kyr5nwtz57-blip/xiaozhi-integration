# 回声消除（AEC）

## 为什么需要

PC/音箱类设备**没有硬件 AFE**（ESP32 官方固件靠硬件做 AEC+降噪+VAD）。
纯软件客户端必须自己做，否则：
- 助手被自己的声音打断
- 用户插话被吞
- 只能做"半双工"（她说话时静音麦克风）——体验极差

## 方案：WebRTC APM

用 WebRTC 的 Audio Processing Module，包含 AEC3。

### 数据流
```
下行 Opus 解码 → 24kHz PCM ──重采样到 16kHz──→ feed_far()  【参考信号】
麦克风 16kHz PCM ──────────────────────────────→ process_near() 【近端】
                                                    ↓
                                            消回声后的 16kHz PCM（上行）
```

### 关键配置
```python
apm = WebRTCAudioProcessing()
cfg = create_default_config()
cfg.echo.enabled = True
cfg.echo.mobile_mode = False        # PC 端用 False
cfg.high_pass.enabled = True
apm.apply_config(cfg)
apm.set_stream_delay_ms(30)         # 播放→采集的物理延迟估计
```

### 处理帧长
WebRTC APM 以 **10ms** 为单位处理（16kHz = 160 样本/帧）。
如果输入是 60ms 帧，要循环切分成 6 个 10ms 帧逐个处理。

## ⚠️ 致命陷阱：参考信号量纲

见 [踩坑实录 坑 1](踩坑实录.md#坑-1aec-参考信号被放大-32767-倍回声消除彻底失效)。

**far/near 的量纲必须一致**。参考信号被意外放大或变形，AEC 会完全失效（实测抑制比
从 40.6dB 掉到 4.3dB）。

## 延迟估计

`set_stream_delay_ms` 要设成"播放写入 DAC → 扬声器发声 → 空气传播 → 麦克风采集"的总延迟。
给小了没关系（APM 会在窗口内自适应搜索），但**别小于真实延迟**。

典型值：30~120ms，取决于声卡缓冲和扬声器/麦克风距离。

## 参考信号喂入时机

**最佳实践**：在播放回调里，把"这一帧真正要送进 DAC 的采样"喂给 `feed_far()`。
这样参考信号与物理回声在时间上精确对齐。

如果在下行收包时喂，会有一整个播放缓冲的偏差。

## 兜底原则

AEC 出错（库缺失、异常）时必须**旁路**——原样透传上行，绝不能让上行断掉。
宁可没有回声消除，也不能让用户说不了话。
